# Local Intelligence 初期版

端末内の検索・関連候補を、既存のSQLite FTS5/trigram、`note_links`、`note_tags`から読み取り専用で求める。Embedding、ベクトルDB、外部AI送信は行わない。

## 関連候補API

`RelatedNotes({ noteId, notebookId?, descendants, limit })` は現在の保存空間の候補を最大20件返す。Notebook scopeは指定なしで保存空間全体、指定ありで直下、`descendants: true`で子孫を含む。候補は直接リンク、バックリンク、共通タグ、対象タイトルの先頭語句とのタイトル・本文一致から収集する。1〜2文字の語句は既存LIKE検索へフォールバックする。Notebook条件とゴミ箱除外を候補取得時に適用してから、リンク・タグ・検索それぞれの候補プールを80件で打ち切る。リンクは相互リンク、更新日時、ID、タグは共有数、ID、語句はタイトル一致、FTS順位（短語は更新日時）、IDの順で選ぶ。単一の共通タグだけの候補は除外する。関連度は直接リンク8、バックリンク7、タイトル一致5、本文一致2、共通タグ最大2を加算し、同点はノートID順とする。これは語句一致であり、意味的同義性は保証しない。

返却するのはID、タイトル、revision、最大160文字の抜粋と最大3件の根拠。本文正本は読み取らず、抜粋は派生FTS索引から取得する。索引revisionが正本と不一致、または検索・リンク索引の更新失敗時はAPI全体を失敗させる。候補の保護・ロック状態が取得できなければ失敗し、保護・ロック・ゴミ箱は返さない。別保存空間のDBは開かない。

既存バックリンク内で保存空間全体／Notebook直下／子孫を含む範囲を選び、「ノートを開く」「参照に追加」を使える。関連候補APIは表示中だけ呼び、閉じる・ロック・保存空間切替では古い結果を破棄する。「参照に追加」は現在の範囲で候補とrevisionを再照会してからIDをAIチャットStoreへ渡す。AI送信時は従来の`PrepareAIContext`が正本とrevisionを再取得し、保護ノートのAI参照禁止と送信前確認を維持する。関連候補自体はノートを変更せず、解析結果はメモリだけに置く。

## 検証

Goの`internal/note/related_service_test.go`で日本語、リンク、索引失敗、revision、Notebook直下・子孫、80件超の範囲外候補、ゴミ箱、タグ更新を確認する。`internal/note/search_repository_test.go`で複数語・短語の一致範囲と抜粋を確認する。`internal/app/related_api_test.go`で解除中も含む保護除外を確認する。`frontend/scripts/test-related-notes.mjs`で古い応答、範囲選択、非表示時の要求抑止、再オープン、参照追加前の再検証を確認する。修正前の5,000ノート・2KB本文の合成データによる`BenchmarkRelatedNotes5000`は、正本ハッシュ照合を含む一回の計測で約107.7ms、約2.05MB、30,803 allocsだった。候補SQL修正後は未計測。Wails画面の描画・操作応答性と実データでの結果品質は手動受け入れが必要。
