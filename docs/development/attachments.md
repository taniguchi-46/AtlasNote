# 添付画像の保存設計

## 方針

添付画像の正本はローカル保存空間に保持し、同期時は既存WebDAVへ添付entityとして複製する。本文の正本は従来どおり `notes/<noteID>.md` とする。本文中にはローカルパスやdata URLを保存せず、次の管理参照だけを保存する。

```text
atlasnote-attachment://<noteID>/<attachmentID>
```

添付の正本は `notes/attachments/<noteID>/` 配下で、`manifest.json` にメタデータ、`<attachmentID>.bin` にPNG／JPEG本体を置く。メタデータをSQLiteへ追加しないため、DB schema migrationは発生しない。

## 制限と検証

- 形式はPNG／JPEGのみ。
- 1画像は10 MiB以内、1ノートは64 MiB以内、1ノート100件以内。
- 画像は幅・高さ8192以下、画素数40,000,000以下。
- MIME、実際の画像デコード、寸法、サイズ、SHA-256をGo側で検証する。
- ファイル名は表示用メタデータとして安全化し、ファイルパスへ直接使用しない。

フロントエンドでも早期検証するが、Wails APIと保存Storeを最終的なセキュリティ境界とする。

## ロック・復旧・バックアップ

保護されたノートの添付本体は、本文と同じロック材料を使うAES-GCMで暗号化し、`noteID` と `attachmentID` を追加認証データへ束縛する。ロックの有効化・無効化・パスフレーズ変更では、本文と添付を同じ操作IDのstage／commit／rollback境界で再エンコードする。ロック中の起動復旧では、鍵を要求する内容検証を行わず、manifestと参照ファイルの構造だけを検証する。

バックアップ、保存場所移行、復元は既存の `notes/` 再帰コピー境界を利用する。未知ファイルを自動削除せず、manifestに参照された本体の欠落・symlink・不正な名前・上限超過は復旧エラーとして停止する。

ノート完全削除では、既存のMarkdown削除ジャーナルと同じ操作IDで添付ディレクトリも退避し、DB削除後に確定削除する。途中終了時は次回起動の削除復旧で再開する。

## 同期と旧版互換性

既存のWebDAV形式へ添付を同期エンティティとして追加する。1添付を1つのobjectとして扱い、manifestには添付キーとobject hashを記録し、object payloadにはmanifestメタデータとBase64化したPNG／JPEG本体を含める。ローカル保存時は既存のnote syncGateで同期・バックアップと排他し、次回同期時にも添付manifestと本体を走査してoutboxへ再構成できる。

同期先からの適用は本文を先に行い、存在するノートへ容量・MIME・寸法・サイズ・SHA-256を再検証してから添付manifestと本体を原子的に保存する。ノートのtombstoneを同期すると、そのノートの添付エントリもリモートmanifestから除去する。保護された本文を含む保存空間は従来どおり同期を拒否し、保護添付を平文同期へ混ぜない。添付を理解しない旧クライアントは未知のentity typeを検証エラーとして停止するため、参照だけを成功扱いにしない。

## UIと非同期境界

Rich本文では管理参照をProseMirrorの画像ノードへ保存し、表示時だけGo APIからBlob URLを作成する。Blob URLはノード更新・ノート切替・破棄時に解放する。Markdown本文では同じ管理参照をMarkdown画像記法へ挿入する。

貼り付け前のノートID、本文、選択範囲、Richのドキュメントに操作世代を付け、非同期保存完了後に再検証する。ノート切替、本文変更、選択範囲変更、ロック、モード変更、挿入失敗が起きた場合は本文を変更せず、保存済み添付と入力データを画面上の再試行状態へ保持する。通常の文字、表、Mermaid貼り付けは画像入力でない場合に既存経路へ渡す。

添付ZIP出力は下書きを保存し、保護ノートでは復号済み画像を平文保存する明示確認を得てからGo側のOSネイティブ保存ダイアログを開く。ダイアログ後にrevision、添付manifest、ロック状態を再検証し、Go側のコンテンツ排他を保持したままmanifestと復号済み画像を原子的に出力する。ログには本文、画像本体、保存先フルパス、タイトルを記録しない。
